# M03 — System Integration: Drawing the Whole Robot, Once

Every integration decision Buddy has made was written down correctly. That
turned out not to be enough.

The ROS contract lived in one file, the pin map in the firmware tree, the
connector genders in a harness document, the protection chain inside a power
analysis, and the MCU state machine in three places at once. Answering a question
that crossed two of them — *what actually stops the wheels if the Jetson locks
up?* — meant opening four documents and holding them in your head. And the one
drawing that had tried to show the whole thing was a hand-made Mermaid block
diagram that still showed a **CAN bridge**, two weeks after
[ADR-0006](../../decisions/ADR-0006-mcu-jetson-bus-usb-serial.md) chose USB
serial.

That stale diagram is the whole problem in one file. A drawing that is not
generated is a drawing that is already wrong; it just hasn't been caught yet.

## What was built

Six figures, each generated from the repository and regenerated by
`python3 tools/build.py` alongside the URDF, the firmware header, the analysis
exports and the website:

| Figure | Answers |
|---|---|
| `ros_graph.svg` | which nodes exist, what they publish, and where the system stops being ROS |
| `control_safety_loop.svg` | what happens between `/cmd_vel` and a wheel turning — and what overrides it |
| `power_one_line.svg` | what is in series with what, and where each rail comes from |
| `interconnect.svg` | every cable, its connector, and the pin each wire lands on |
| `fault_state_machine.svg` | the seven MCU states, every transition, all eight fault bits |
| `startup_sequence.svg` | boot to motion, and the gate on each step |

They are indexed from one page —
[`docs/system_model/system_integration.md`](../../system_model/system_integration.md) —
which is now the entry point for the integration picture.

## The design decision: topology is data, layout is code

The obvious way to draw six diagrams is to draw six diagrams. That reproduces the
Mermaid failure six times over.

Instead the *topology* — which node publishes which topic, which block connects
to which over what bus, which rail feeds what — moved into
`docs/system_model/integration_map.yaml`, and only the **layout** lives in the
drawing scripts. The map is held to a strict rule inherited from the parametric
build: it may not contain a number that `design_params.yaml` or the requirements
yaml already owns. Where a diagram needs one it writes a reference —
`param:power.protection.main_fuse_a` — resolved to the live value at draw time.

The effect is small and worth stating precisely: **the fuse rating in the power
diagram is not a copy of the fuse rating. It is the fuse rating.** Change
`design_params.yaml` and the drawing changes with the validator that enforces it.

## The part that makes it stick

A generated diagram can still be generated from a wrong description. So the map
is checked against the files that actually own each fact, as the first step of
every build:

| Check | Asserts |
|---|---|
| **B** | `pin_map.md` agrees with the firmware's `pins.h`, pin by pin |
| **C** | the KiCAD generator's net table puts every signal on the pin the map assigns |
| **D** | states and fault bits match `drive_protocol.md` exactly |
| **E** | the topics `ros_bridge_node.py` really creates are the topics the graph draws |

Checks are worth nothing untested, so each was verified by breaking something on
purpose. Changing one INA pin from `PB0` to `PB9` in the pin map fired **B** and
**C** together — the firmware disagreed and so did the schematic. Renaming the
`UNDERVOLT` fault bit fired **D**. Check **E** found a real (if minor)
discrepancy on its first run: the map claimed the bridge published
`/diagnostics`, which is planned but not yet implemented, and the checker was too
strict — it now allows a `planned` topic to be absent from the code, while still
refusing to let the code publish anything the diagram doesn't show.

Layout is checked too. Each figure audits its own geometry before it is written:
every box, label and edge tag is bounds-checked against the canvas and against
every other element. This caught eight collisions in the first ROS graph and
nineteen in the first interconnect drawing. It matters more than it sounds —
a diagram whose labels are placed by hand degrades the moment a parameter change
makes one of them longer. Verified independently against real browser font
metrics: 417 text elements across the six figures, zero collisions, nothing
out of bounds.

## The second KiCAD sheet

The existing schematic covered the drive harness and deliberately stopped there,
so the pack, the protection chain, the regulated rails and every Jetson↔sensor
link had no drawing at all. `system_wiring` adds them, generated by
`tools/kicad/gen_system_wiring.py` and asserted net-by-net by
`check_system_wiring.py` against an independently written expectation — 16 nets,
including the one that matters most: `+12V_BUS` originates at the E-stop
contactor's output, so every motor amp is downstream of the E-stop, and the
`ESTOP_STATE` line the MCU reads is only an auxiliary contact.

The two sheets meet at shared net names, so a rail can be followed across both.

Drawing the system sheet forced two facts into the open that no document had
stated:

- **The LD19 is not on the 5 V rail.** The D300 kit's USB adapter draws the
  LiDAR's 0.9 W from a Jetson USB port, which puts it inside the Jetson's power
  budget rather than the logic rail's. The integration map said otherwise until
  the schematic made the question unavoidable.
- **The BNO086 sits on a different 3.3 V rail** from the encoders — the Jetson's
  40-pin header, not the Nucleo's LDO. Two nets, `+3V3_JETSON` and `+3V3`, that
  a block diagram would have merged into one.

## What went wrong

**The build had never run on Windows.** Attempting the first full rebuild failed
three times over: `marimo` wasn't installed, then `write_text` died on the `η` in
a derivation because Python defaults to the host's cp1252 encoding, then the
generated markdown came out carrying `docs\analysis\...` backslash paths into a
committed file that a macOS reader would copy as a shell command. All three are
now fixed — every generator writes UTF-8 with explicit LF endings, and a
`.gitattributes` keeps `core.autocrlf` from rewriting the generated tree on
checkout. Lesson: "the build is reproducible" is a claim about the machines you
have actually run it on.

**The schematic generator wasn't deterministic.** It assigned `uuid4()` to every
element, so regenerating an unchanged schematic produced a completely different
file — 498 lines of diff carrying no information. UUIDs are now derived with
`uuid5` from a stable key. The same bug existed in the KiCAD PDF export, where
kicad-cli stamps a wall-clock `/CreationDate`; that is rewritten to the sheet's
own date, same byte length so the xref table stays valid. Consecutive builds are
now byte-identical across figures, schematics, PDFs and documents alike.

**The verifier could not run on the machine it was needed on.**
`check_drive_wiring.py` hard-coded the macOS path to `kicad-cli`, so the
"connectivity is machine-checked, not visually claimed" property was true only on
one laptop. Resolution now searches `$KICAD_CLI`, then `PATH`, then each
platform's usual install location.

## Where this leaves the project

The figures make the remaining gaps easy to point at, which is most of their
value before hardware arrives:

- the 8 A current limit is **drawn but not measured** — it sits on the safety
  path and is bench-verify item 5 in `electrical_interfaces.md`;
- the velocity PID and mid-pulse current sampling compile but have never seen a
  motor;
- sensor extrinsics are placeholders until mounting;
- and every hardware block on all six figures is still `proposed` — decided in an
  ADR, not yet bought.

Next milestone is the purchase gate, and then the electronics bench, where the
red boxes in figure 2 stop being design intent and become measurements.
