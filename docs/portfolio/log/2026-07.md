## 2026-07-11 — Repo declutter, motor sizing, and ADR-0003
**Tags:** calc, decision, process
- **Declutter:** cut the repo from 227 to 106 tracked files — deleted ~19
  template-only research folders, 7 stub ROS packages, duplicate requirements
  files. Removed the `(_IP)` filename convention entirely (files are always in
  progress; the suffix broke path references). Drafts now carry an in-file
  `WIP:` note; an ADR marks a topic settled.
- **Motor sizing (calc):** built the per-wheel torque envelope for the 20 kg
  skid-steer base (r = 0.06 m, 4 driven wheels). Key finding: **pivot-in-place
  tire scrub on carpet sets the stall requirement** — 2.9–3.8 N·m/wheel at
  μ = 0.6–0.8, well above the worst straight-line case (1.47 N·m at 5° ramp +
  0.5 m/s² with SF 2.0). The existing `torque_sweep.py` didn't model scrub;
  derived it from the resisting yaw moment about the pivot center.
  Figure: `assets/figures/torque_envelope.svg`.
- **Decision:** 4× goBILDA 5203 Yellow Jacket 26.9:1 (223 RPM, 3.73 N·m stall,
  $54.99 ea) — the only shortlisted motor clearing the pivot band. Pololu 37D
  (2.65 N·m) and DDSM115 hub servos (2.0 N·m) fall inside/below it. Recorded in
  `docs/decisions/ADR-0003-drive-motor-selection.md` (Proposed; purchase pending).
- **Tension logged:** $220 of the $300–600 budget on motors collides with
  LiDAR + RGB-D + battery (design conflict #4). Fallback documented: cut gross
  mass toward ~10 kg and rerun with JGB37-520-class motors.
- **Portfolio system established** (this log, milestone reports, figures-as-code
  convention in `docs/portfolio/README.md`). Milestone report M01 written.
- **Wheel selection (decision + calc):** caught that the 0.06 m wheel radius used
  in sizing was an unsourced URDF placeholder. goBILDA traction wheels max out at
  96 mm; selected **4× Hogback 96 mm** (crowned tread purpose-built to reduce
  skid-steer scrub — directly attacks our dominant load case) + 8 mm REX hubs,
  ~$76 all-in (ADR-0004). At r = 0.048 m: design case 1.47 → 1.18 N·m, pivot band
  2.29–3.05 N·m → 22% stall margin at μ = 0.8 (was marginal). Trade accepted:
  **ground-clearance requirement amended 0.05 → 0.038 m** (the 0.05 was a round
  guess; indoor thresholds are 5–20 mm). Cascade: requirements yaml, URDF params
  (incl. base_center_z 0.10 → 0.088 to keep axle height = wheel radius so sim
  wheels touch ground), envelope figure + CSV regenerated, derivation doc
  substitutions redone, M01 postscript. Lesson: a "placeholder" number that feeds
  a real decision isn't a placeholder — audit inputs for unsourced values.
- **Parametric build system (process):** identified that design values lived in
  five hand-synced places (requirements yaml, xacro, CLI defaults, figure
  constants, markdown prose) — today's wheel change required manually chasing
  every substitution, and a hand-rounding error (3.06 vs computed 3.05 N·m) had
  already crept in. Built the fix: `design_params.yaml` (choices/assumptions) +
  requirements yaml (requirements, no overlap) → `buddy_calcs/` loader+equations
  → everything downstream is generated by `python3 tools/build.py`: the URDF
  params file (now marked GENERATED), the derivation docs (marimo notebooks in
  `docs/analysis/*.py` whose substituted numbers are computed, exported to the
  committed `.md`), both figures, and the sweep CSV. Verified end-to-end: changed
  SF 2.0 → 1.5, one build propagated 1.18 → 0.88 N·m through derivation, figure
  legend, annotation, and CSV; reverted cleanly; consecutive builds are
  byte-identical. Bonus catch: the FBD had been drawing wheels at the stale
  120 mm — parametrization fixed it automatically. Lesson: numbers that appear
  in more than one file need a build step, not discipline.
- **Derivation convention added** (same day, after review): calculations must be
  presented as checkable derivations — governing equations, symbol tables, numeric
  substitution, units check, limits of validity — so a reviewing engineer can
  verify every number by hand. First instance:
  `docs/analysis/drive_torque_and_pivot_scrub.md`, with a two-panel free-body
  diagram figure (`tools/figures/plot_drive_fbd.py`) covering the ramp FBD and the
  pivot moment balance.

## 2026-07-14 — Interface verification, drive protocol v1, firmware compiles
**Tags:** calc, decision, build, test
- **Interface verification** (`docs/system_model/electrical_interfaces.md`):
  purchases proceed on the assumption motors ↔ VNH5019 ↔ G474 ↔ Jetson
  interoperate — now checked signal-by-signal with numbers instead of hope.
  Highlights: everything is 3.3 V-native (VNH5019 logic high ≥ 2.1 V), zero
  level shifters; TIM1 @ 170 MHz → 20 kHz PWM at ~13-bit resolution; CS gives
  1.12 V at the 8 A limit into a 12-bit ADC (~5.8 mA/LSB); VCP link has 18×
  bandwidth margin; MCU powered from the 5 V rail so both failure directions
  (Jetson dies / MCU dies) land safe. Five-item bench-verify list for what
  paper can't close.
- **ADR-0006 — bus decision:** USB serial via the Nucleo's ST-LINK VCP for
  v0.1 (zero hardware, huge margin); CAN-FD reserved for the arm era (G474 has
  FDCAN on-chip); micro-ROS rejected because the MCU must stay safe with ROS
  entirely absent.
- **Drive protocol v1, implemented twice on purpose:** framed 0xB5DD +
  CRC-16/CCITT-FALSE + seq + version; CMD_VEL/CMD_MODE/PING/TELEMETRY/PONG/
  FAULT_EVT; 200 ms watchdog rule (REQ_SAFE_002); E-stop dominance; MCU-side
  velocity clamp. C implementation (no deps, no allocation, resynchronizing
  parser) compiles into firmware AND host tests; Python mirror for the Jetson
  bridge; **golden vectors assert byte-identity between the two** — the ends
  cannot drift silently.
- **Mock MCU** (`mock_mcu.py`): full state machine + watchdog + wheel model
  over a pty — the future `buddy_base` bridge node gets integration-tested with
  zero hardware. 10 behavioral self-tests pass.
- **Firmware compiles for the real target:** pure-C safety state machine
  (host-tested: 19 checks incl. "E-stop release does not auto-run" and "cannot

  timers, TIM1 PWM, CS ADC, fault GPIOs), superloop with telemetry at 100 Hz.
  PlatformIO/GCC for NUCLEO-G474RE: **16.4 kB flash, 1.5 kB RAM**. Firmware

- One command runs every host-side test: `tools/run_protocol_tests.sh`
  (C protocol, C state machine, Python protocol, mock MCU — all green).
- Lesson: writing the protocol twice with golden vectors caught nothing today

## 2026-07-12 — Power budget: the stall-current fear, resolved by design
**Tags:** calc, decision
- **The fear:** 4 × 9.2 A motor stall + Jetson + sensors looked like an
  impossible/unaffordable battery worst case. **The resolution:** stall current
  is a fault condition, not an operating point — the motor drivers' adjustable
  current limit turns the worst case into a *chosen* number. Designed ceiling:
  8 A/motor → 37 A bus peak including system loads, vs 42 A unlimited fault.
- **The validator earned its keep on first run:** the initial 7 A limit choice
  only allowed 2.81 N·m — below the 3.05 N·m worst-case carpet pivot. Raised to
  8 A (allows 3.23 N·m) and scaled the protection chain to match (BMS ≥ 40 A,
  fuse 50 A). `tools/build.py` now enforces these inequalities on every build
  (`buddy_calcs/power.py::validate`).
- **Architecture (ADR-0005):** 3S Li-ion + BMS (chosen over RC LiPo for the
  hardware protection layer near people/pets); motors direct on the bus; Jetson
  behind a regulated 12 V buck (dev kit input 9–20 V verified — sag can't brown
  out compute); protection chain driver-limit → BMS → 50 A slow-blow fuse → E-stop.
- **Capacity:** unchosen camera/LiDAR carry ≤ 5 W *reserved allocations* that
  become hard selection constraints. Allocation model (everything at full
  reserve): 66 W avg → 92 Wh → **3S ≥ 8 Ah, ~$60–100** guarantees the 60-min
  requirement; expected usage (46 W) gives ~85 min. Peak is a mild ≈ 4.5C —
  the peaks never drove the sizing; runtime did.
- New parametric analysis: `design_params.yaml` power section +
  `buddy_calcs/power.py` + `docs/analysis/power_budget_and_battery.py` notebook +
  `assets/figures/power_budget.svg`. Superseded and deleted the all-TBD
  `docs/hardware/power_budget.yaml` and `tools/calculators/battery_sizing.py`.
- **Carried forward:** motor driver selection now has a HARD requirement —
  adjustable ~8 A per-channel current limit (in-driver or current-sense + MCU).
- **Motor driver shortlist (decision pending purchase):** compared RoboClaw
  2x15A (premium, $260), TB67H420FTG (hardware current chop but 3.4 A continuous
  — only 10% over the 3.1 A sustained case, thermally thin), BTS7960 ($35,
  crude), and **4× Pololu VNH5019 carriers (~$100, recommended)** — 12 A/30 A
  per channel, 140 mV/A current-sense into the G474's ADCs for the 8 A firmware
  limit, hardware overcurrent backstop. The firmware limit sits on the safety
  path → mandatory bench verification before rolling. Bonus: the dual-VNH5019
  Arduino shield stacks directly on the NUCLEO-G474RE for the first bench loop.
  Doc: `docs/research/hardware/electronics/motor_drivers/driver_selection.md`.
- **Purchasing checklist created:** `docs/financials/SHOPPING_LIST_v0_1.md`
  (temporary) — full v0.1 cart ≈ **$540** of the $300–600 budget: drivetrain
  $292, electronics + power $249. Conflict #4 quantified, trim options listed.
- **Portfolio website generator built** (`tools/site/build_site.py`, runs inside
